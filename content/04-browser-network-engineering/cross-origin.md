# 什么是跨域？你是怎么解决的？

## 30 秒回答

同源策略要求协议、域名、端口三者一致，不一致时浏览器会把 fetch 或 XHR 的响应拦下不给脚本使用，这就是跨域。要注意它是浏览器行为，curl 或 Postman 不受限制，说明它是安全机制而不是网络故障。我的解决方式：开发环境用 Vite 的 server.proxy 把请求转发到后端；生产环境让页面和接口走同域，我的三个项目上线时就是通过 Nginx 反代把接口收进同一域名下，必须跨域时再由后端配置 CORS 响应头。

## 标准回答

先说清边界：同源策略限制的是"读取跨源响应"，img、script 这类标签加载资源不受此限制，但这也正是 CSRF 和 JSONP 时代的历史背景。带自定义头（比如 Authorization）的请求会触发预检：浏览器先发 OPTIONS 询问服务器是否允许，通过后才发真实请求，所以调试跨域问题时要注意 OPTIONS 请求的状态。

我的实际做法分环境。开发环境前后端端口不同，直接跨域最简单的方式是在 Vite 配置里加 server.proxy，把 /api 前缀转发到后端地址，浏览器看到的是同源请求。生产环境我的项目都部署在自己的服务器上，用 Nginx 把前端静态资源和后端接口挂在同一个域名下，从源头避免跨域；这样 Cookie 和凭证处理也简单。

如果是必须分开域名的场景，就由后端设置 Access-Control-Allow-Origin 等响应头，前端在需要凭证时打开 withCredentials，同时后端不能把来源写成通配符，Cookie 还要配合 SameSite 策略，否则会被浏览器拦截。

排查跨域问题时我先看 Network 面板里请求的实际状态码和响应头，确认 CORS 头是否存在、预检是否通过，而不是笼统地归因为"跨域问题"。

## 回答要点

- 点出"浏览器行为"和"预检请求"这两个理解深度的标志。
- 开发代理和生产同域是两条不同链路，分开讲。
- 用自己项目的部署方式（Nginx 同域）落地。
