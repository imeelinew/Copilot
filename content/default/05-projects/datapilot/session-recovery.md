# 城市视图登录、刷新和 401 清理是怎么串起来的？

## 核心回答

城市视图的请求层从 Redux 读取 token，统一加 Authorization，遇到 401 就清理认证状态。应用启动时先恢复用户和 token，再由 `RequireAuth` 判断是否能进入受保护页面；登录成功后再进入 dashboard。持久化只保存恢复登录所需的轻量身份信息，业务列表和图表结果仍从接口重新获取，避免把过期数据当成真相。

## 追问：为什么菜单和路由都要保护？

菜单过滤负责不让用户看到无权入口，`RequireAuth` 负责直接输入 URL 时的页面拦截，两者解决的是不同路径。真正的接口权限还必须在后端校验，浏览器里的角色字段可以被改，不能作为授权依据。当前前端权限矩阵需要和后端规则持续对照，不能把前端放行当作最终安全结论。

## 追问：并发请求同时 401 怎么处理？

清理认证状态和跳转动作应该做成幂等操作，避免每个请求都重复 toast 和 history 跳转。更完整的方案会在请求层统一维护刷新锁：第一个请求尝试刷新，其余请求等待结果，刷新失败再一次性退出。当前实现以清理和保护页面为主，这个并发刷新策略需要按后端是否提供 refresh token 再补。
